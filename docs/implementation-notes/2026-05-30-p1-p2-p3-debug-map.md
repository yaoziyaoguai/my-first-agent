# P1/P2/P3 Debug Map — 2026-05-30

## P1: Planner → ActionPlan → Scheduler 断链

### 根因

两个独立 schema 之间无桥接：

| | Plan (planner 产出) | ActionPlan (scheduler 消费) |
|---|---|---|
| **步骤单元** | `PlanStep` | `ActionNode` |
| **ID 字段** | `step_id` | `node_id` |
| **类型字段** | `step_type` (read/analyze/edit/run_command/report/collect_input/clarify) | `action_type` (TOOL_CALL/MEMORY_RETAIN/SKILL_SELECT/...) |
| **工具字段** | `suggested_tool` (Optional[str]) | `target` (str, required) + `params` (dict) |
| **依赖** | 无（隐式顺序） | `depends_on` (显式 DAG) |
| **失败恢复** | 无 | `recovery` (ActionRecoveryPolicy) |
| **条件跳过** | 无 | `condition` (condition flag name) |

**涉及文件**：
- `agent/plan_schema.py:7-43` — PlanStep 定义
- `agent/action_scheduler.py:65-105` — ActionNode 定义
- `agent/action_scheduler.py:498-557` — `build_action_plan_from_dict()` (dict→ActionPlan)
- `agent/action_scheduler.py:560-633` — `build_action_plan_from_model_output()` (JSON string→ActionPlan)
- `agent/planner.py:50-115` — `generate_plan()` 返回 Plan 对象
- `scripts/real_evidence_008_model_generated_plan.py:232` — 使用 `provider.create()` 绕过 `core.chat()`

### 当前证据

- Gap B: `build_action_plan_from_model_output()` 7/7 tests PASS — JSON→ActionPlan 桥接正确
- Model Plan: 13/13 PASS — real provider → model JSON → bridge → scheduler evidence
- **但**: model 调用使用 `provider.create()` + custom system prompt（非 `core.chat()` 路径）
- **缺失**: Plan (planner 产出) → ActionPlan 转换；`core.chat()` → model plan → scheduler 闭环

### 为什么还不是 credible

1. `planner.generate_plan()` 产出 `Plan`，无法被 `ActionScheduler` 消费
2. 008 model script 的 `provider.create()` 是旁路，不是 main runtime path
3. 没有 Plan→ActionPlan 转换器——这是 planner 和 scheduler 之间的 schema gap

### 最小修复路径

1. **新增 `plan_to_action_plan()` 转换器**（`agent/action_scheduler.py`）
   - 输入: `Plan` 对象
   - 输出: `ActionPlan` 对象
   - 映射规则: `step_type` → `action_type` (read→TOOL_CALL(read_file), edit→TOOL_CALL(write_file), run_command→TOOL_CALL(bash), analyze→TOOL_CALL(read_file), report→TOOL_CALL(read_file), collect_input→TOOL_CALL(request_user_input), clarify→TOOL_CALL(request_user_input))
   - step_id → node_id
   - suggested_tool → target (fallback: step_type 推断)
   - title+description → description
   - 隐式顺序 → depends_on (step_N depends_on step_N-1)

2. **Contract tests** — 验证 Plan→ActionPlan 转换正确性

3. **Validation script** — real provider → planner.generate_plan() → plan_to_action_plan() → core.chat(action_scheduler=scheduler) → evidence

### 测试计划

- `test_plan_to_action_plan_converts_all_step_types` — 7 种 step_type 映射
- `test_plan_to_action_plan_sequential_depends_on` — 隐式顺序→显式依赖
- `test_plan_to_action_plan_suggested_tool_becomes_target` — 工具映射
- `test_plan_to_action_plan_empty_steps_raises` — 空 steps 边界
- `test_plan_to_action_plan_preserves_goal_and_description` — 元数据保留

## P2: Checkpoint Save Trigger 在 Real Provider Conversation 中未触发

### 根因

`_dispatch_checkpoint_save()` 只有 3 个调用点：

| 位置 | 触发条件 | Source |
|------|---------|--------|
| `core.py:812` | memory confirmation → awaiting_user_input | `"memory_confirmation"` |
| `core.py:1045` | conversation compression + task.current_plan 存在 | `"compression_sync"` |
| `core.py:1101` | plan generation → awaiting_plan_confirmation | `"plan_confirmation"` |

**关键发现**：简单的 real provider 对话（无 memory/planning/compression）永远不会触发 checkpoint save。这是按设计行为，不是 bug——但这意味着普通对话无法产生 checkpoint evidence。

### 涉及文件

- `agent/core.py:304-340` — `_dispatch_checkpoint_save()` 定义
- `agent/core.py:812` — call site 1 (memory confirmation)
- `agent/core.py:1045` — call site 2 (compression sync)
- `agent/core.py:1101` — call site 3 (plan confirmation)
- `agent/runtime_integration/checkpoint_save.py` — CheckpointSaveHandler

### 当前证据

- Part A: 10/10 PASS — checkpoint save/resume dispatcher evidence chain
- Part B: 2 CONCERN — tools executing but no save point reached
- 004 整体: CLOSED (hardened)

### 为什么还不是 credible

1. Real provider 普通对话无法触发 checkpoint save——只有特定状态转换才触发
2. 004 Part B 的 2 CONCERN 证实了这一点
3. 缺乏"每次 turn 结束自动保存"的选项

### 最小修复路径

1. **新增 turn-end checkpoint save**（`agent/core.py`）
   - 在 turn-end hooks 处理完成后、下一轮 model 调用前
   - 通过 `chat(checkpoint_save_on_turn_end=True)` 参数控制
   - 默认 False（向后兼容）
   - 当 dispatcher 不可用时静默跳过

2. **Validation script** — real provider conversation with `checkpoint_save_on_turn_end=True` → CHECKPOINT_SAVE evidence → verify checkpoint file

3. **更新 004 debt** — 记录 turn-end save 路径已就位

### 测试计划

- `test_turn_end_checkpoint_save_dispatches` — dispatcher 可用时产生 evidence
- `test_turn_end_checkpoint_save_no_dispatcher` — dispatcher=None 时静默跳过
- `test_turn_end_checkpoint_save_default_off` — 默认不触发

## P3: Model-Owned Skill Selection / Confirmation Path

### 根因

**Skill Selection**:
- `select_skill_for_real_provider()` 使用英文词分割——中文 prompt 无法匹配英文 skill name/tag
- `core.chat()` 内部构建自己的 skill_registry——架构限制，无法从外部注入多 skill
- 当前 002 evidence 全部 prompt-steered（输入含 "demo"）

**Confirmation Path**:
- production 默认 `confirmation='always'`——所有工具调用都需要确认
- 007 使用 `confirmation='never'` override 验证 tool pipeline
- confirmation='always' 的完整用户交互路径未在 real provider 下验证

### 涉及文件

- `agent/skill_selection.py` — `select_skill_for_real_provider()` 关键词匹配
- `agent/core.py` — `chat()` 内部构建 skill_registry
- `agent/confirmation/tool.py` — `handle_tool_confirmation()`

### 当前证据

- 002: real provider SKILL_SELECT 6/6 PASS (prompt-steered)
- 002 hardening: 9 PASS / 3 FAIL / 5 CONCERN

- 003 hardening: 6 PASS / 1 FAIL / 8 CONCERN / 1 SKIP

### 为什么还不是 credible

2. 多 skill 竞争场景无法在 `core.chat()` 中测试（架构限制）
