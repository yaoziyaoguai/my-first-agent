# 从通用工具底座到可靠编码助手：能力审计

日期：2026-09-13。对象：当前 `main` 工作树，包括既有未提交修改，不是只审计 HEAD。
本轮为评估，不实施升级、不调用付费模型、不改变权限、不提交或推送。

## 结论与证据边界

当前项目有值得保留的受控执行底座，但没有足够证据证明它已经是能稳定处理复杂仓库任务的
Coding Agent。“工程保护做得较多，实际编码能力的验证和使用路径做得较少”比“没有能力”准确。

需要纠正此前过宽的产品判断：最近真实模型通过的 K1–K5 主要覆盖 TODO 读取、配置读取、
小报告生成、指定脚本执行和标点编辑。它们不等价于自主定位 bug、跨文件修改、选择测试、
理解失败并修复。3502 条回归测试通过是既有工程证据，不是 Agent 自主解决 3502 个问题。
相反，缺少复杂任务测评也不能证明它必然做不了复杂任务；目前缺的是可靠性证据。

当前适合的定位：有人监督的文件与命令助手、可研究的 Agent 执行底座。
尚不适合承诺：独立接手中等仓库需求并稳定交付，或无人监督处理任意软件工程任务。

## 应保留的已有能力

- 唯一 Runtime、ContextManager 和 ToolRuntime 的所有权边界；扩展复用它们。
- 文件搜索、分块读取、精确编辑、目录创建、受控进程和原生 sandbox/shell。
  不是“没有 shell”，也不是“只能改一个文件”；现有工具可组合完成多文件工作。
- 审批、文件变化校验、执行前后 checkpoint、未知结果恢复和累计模型请求预算。
- 文件/进程/来源证据、会话恢复、上下文压缩及受治理的扩展入口。

这些保护有实际价值，但“工具可调用”“执行可追踪”和“任务做正确”是三个不同层次。

## 按收益排序的问题

### P0：缺少有代表性的真实编码基线，无法判断哪些优化真的有用

依据：`docs/handoffs/2026-09-13-daily-use-repair-v3/RESULTS.md` 的 K1–K5；
`tests/process/test_j1_production_verified_done.py:43` 的 provider 是按调用序号返回预设动作的
测试替身。这类测试能验证 production 执行路径，但不评估模型是否会自主选择正确动作。

影响：容易把修复一次协议错误、增加一个扩展、提高回归用例数当成能力提升。
此前部分复杂扩展的真实失败是历史证据，修复后未重测的不能直接列为当前仍失败。

最小下一步不是新评测平台：用现有启动入口跑一小组固定的真实仓库任务，记录初始快照、
最终 diff、独立验收结果、模型与配置、请求/成本、耗时和人工介入。先选三个小案例建立
运行方式，再扩展为约十二个 bug/功能/重构/中断恢复案例；保留未用于调提示词的验收用例。
任务规模和通过门槛是待冻结的产品合同，不是本轮已有成绩。

### P1：验收擅长证明“执行过”，对“做对了”的判断仍偏弱

依据：`agent/runtime/evidence.py:1216` 校验 process receipt、命令指纹、退出码及可选输出摘要。
这是执行真实性验证，不是业务正确性、测试覆盖范围或测试集完整性的判定。
当前 `state.py:654` 的过程义务主要由用户文本规则建立。

本轮离线探针：

| 合成用户输入 | `_local_process_requirement` |
|---|---|
| `修复这个 bug，并运行测试。` | `True` |
| `修复这个 bug，并确保全部测试通过。` | `True` |
| `Fix the bug and run the tests.` | `True` |
| `Fix the bug and make all tests pass.` | `None` |
| `不要运行测试，只解释原因。` | `False` |

这里证明的是同义要求没有一致建立必需过程义务，不是完整真实模型任务必然不测试。
不能靠持续增加自然语言正则来承担所有软件需求理解；也不能反过来让模型自行扩大权限。

建议：先选一类编码任务，把独立验收命令、必须修复的失败行为和必须保留的既有行为固定下来；
复用现有 receipt 证明命令确实运行，并由验收用例判断行为。测试结果必须对应最终交付代码，
不能改完代码后沿用旧测试成功结论。对测试删除、跳过或只运行无关测试保留外部检查。
这不要求为所有语言创建通用测试结果框架，也不要求每改一行就跑全量。

### P1：默认调用预算与控制成本更适合短任务，复杂任务连续推进尚未证明

依据：`main.py:204` 每次用户 action 最多八次模型调用，可由后续 `/resume` 继续；
不是整个任务永远只能八次。最近 K1/K2 的简单只读旅程各用了三次模型请求，K4 的指定
脚本和回读用了五次；K1/K2 还各出现三次数据外发确认。

影响：探索、修改、测试和修复要争用有限步数，控制/确认成本在短任务中已可见。
当前 OpenAI-compatible adapter 为非流式：`agent/provider/openai_http.py:75`。
`agent/provider/config.py:56` 明确不保存 provider-specific reasoning continuity；
显式 thinking 仅支持 `disabled` 或不传字段。不传不等于所有后端都关闭推理，
但不能据此承诺已经完整支持任意推理模型的连续工具使用。

建议：先测有效工作调用占比，验证一个明确支持的模型/协议组合，再决定预算和流程调整。
在任务总成本、时间、取消和停滞上限下连续推进；不要单纯放开无限循环。
权限体验若要改善，应另行明确工作区、文件类别、命令和外发目标的授权范围，
不能静默替用户批准。可见进度和取消是基本体验，不应包装为推理能力提升。

### P1：仓库理解与多文件修改缺少经过验证的完整工作方式

依据：`agent/tools/file_ops.py:35` 的默认搜索最多打开 200 个文件、读取总计 2 MB、
返回 16 个匹配；单文件读取有 200 KB 限额。精确文本编辑要求唯一匹配。
在当前入口/源码检查中未发现自动加载仓库分层 `AGENTS.md` 的产品路径；
本次 Coding Agent 使用的 Graphify 是开发辅助，不属于产品检索能力。

这些限制本身不是 bug；现有 shell 也可以补充检索与 diff。因此不能得出“没有 LSP 就不会编程”
或“必须先造 AST 索引”的结论。真正未证明的是能否持续找到正确文件、理解依赖、保留用户
已有修改，并交付可审查的完整改动。

建议：先稳定仓库入门路径——安全读取项目说明、识别构建/测试入口、范围化搜索、查看相关调用方、
聚焦修改并检查整体 diff。沿用现有工具，只有实测出现搜索缺口或编辑摩擦才增加接口。
任务工作记录优先保存当前目标、相关文件、已试失败方案、验证命令和下一步，而不是堆聊天记忆。
已有压缩保留未闭合尾轮，见 `agent/runtime/context.py:309`；这有安全理由，但不能把“支持
长会话压缩”直接当成超长单任务不丢信息的证明。

### P1（Web 开发场景）：浏览器与本地开发验证无法直接接通

依据：`agent/browser/url_policy.py:135` 只接纳公网 HTTPS，拒绝 localhost、IP 字面量、
非默认端口及解析到私网/回环的域名。本轮注入合成 resolver，无网络请求，复现：

- `http://localhost:3000` → `scheme_not_https`。
- `https://localhost` → `localhost_not_allowed`。
- 合成域名解析为 `127.0.0.1` → `non_public_address`。

这是既有公网浏览器合同的正确执行，不是该安全检查写错了；但与本地 Web 编码任务不匹配。
现有 `shell_exec` 为有界、一次性、网络关闭的命令，不是已经产品化的开发服务器生命周期。

建议：若 Web 开发是目标，单独设计由用户授权的本地应用 origin、受管开发进程、日志和停止入口，
让同一 Runtime 可以启动项目、读错误、操作本地页面、验证功能并收尾。
保留公网浏览器防 SSRF；不笼统开放私网、不接管用户已登录浏览器、不新增登录项或常驻服务。
若近期只做 Python/CLI 任务，此项应排在稳定编码基线之后。

### P2：SubAgent 只是单次文字顾问，不是能分担编码工作的执行者

依据：`agent/subagent/runner.py:41` 固定一次模型调用；`:63` 无 ContextSource、无工具，
系统提示明确只有一次回答。它只能分析父 Agent 交给它的文本，不能独立浏览仓库和运行测试。

建议：先把主 Agent 的单任务完成率做上去。之后如确有瓶颈，先做有读取权限、预算有限、
返回文件位置证据的仓库调查助手；父 Agent 保留写入所有权。不要直接开启任意并行写入或 Agent 群。
更多 Agent 会增加调用成本和协调成本，不自动提高正确率。

## 哪些做重了，哪些做轻了

做重：相对已验证的任务价值，Goal/evidence 控制、身份绑定、扩展验收和用户确认占比偏高；
核心 `loop.py` 4341 行、`state.py` 3967 行、`contracts.py` 5891 行使修改与理解成本明显。
行数只是维护风险信号，不是机械拆文件的依据。`state.py` 同时包含自然语言要求分类与具体
工具证据准入，值得在编码闭环变更触及它时审查边界，不为审计结论立即重构。

做轻：真实任务成功率、独立验收、仓库工作流、模型协议适配、长任务连续性和可见操作体验。
已有 Memory 主要是受预算的词法召回（`agent/memory/source.py:38`），不是完整的工程工作记忆；
优先改进任务交接事实，不优先造向量数据库。

文档漂移也已出现：`docs/architecture/KERNEL_ARCHITECTURE.md:60` 仍写 Everyday 使用 `None`
不中断累计调用，而当前 `main.py:204` 是每 action 八次。下一次相关实现应同步修正这一说明。
本轮不把既有会话容量 256、跨平台 promotion 或更多 MCP 连接列为编码能力跃迁的前置条件。

## 建议只推进三步，不启动新一轮能力堆叠

1. **建立真实编码基线**：一个跨文件 bug、一个小功能、一个中断恢复任务，真实模型执行，
   独立测试判定。先识别失败主要来自模型、检索、工具、控制还是环境。
2. **打通一条编码闭环**：只修基线暴露的共同瓶颈。以“查明问题、改动、针对性测试、
   分析失败、修复、最终 diff 和相关回归”为完整单元，不是完成一个工具调用就结束。
3. **验证稳定性与扩展收益**：增加未参与调参的任务、重复运行易失败任务；确有需要再加入
   本地浏览器验证或只读调查助手。

建议的验收样例：在陌生小仓库中完成需要修改 4–8 个文件的 API 变更；独立失败测试转绿，
既有相关测试不退化，用户未提交修改保留；人为中断后恢复不会重复副作用，最后的用户修正仍生效。
文件数只是任务规模描述，不能当成能力分数。预算内未完成就如实计失败/暂停，不由我接手补完
再计入 First Agent 的成绩。更换模型、提升权限、提供解题提示都须单独记为条件变化。

不建议现在优先做：全平台 sandbox、新的 scheduler、更多连接器、无限记忆、自动自修改、
多 Agent 群、机械消灭大文件，或另建第二套 coding loop。

## 通用 Agent 的诚实评价

通用 Agent 不是全无价值，但通用的是工具组合与交互方式，不是保证任意任务都正确。
常见风险包括：需求含糊时自行补全；长链路中遗忘约束或重复失败；以能执行替代正确性；
外部文本影响决策；时间和费用波动；把测试、监督、环境准备的成本转移给用户。
这些是需要测量和约束的失败模式，不意味着每种模型、每个任务都有相同失败率。

对于本项目：作为学习和受控执行底座有价值；作为“已经可靠的自主编码产品”，当前证据不足。
继续堆模块而不测真实完成率，确实可能变成复杂但不好用的软件。最有价值的转向是：
少增加能力名词，让一个真实编码任务完整、稳定、可验证地完成。
