## 1. 必须继续修的日常阻断

### R1 / 高优先级：两项必需验证没有正常的生产收尾路径

定位：`agent/runtime/evidence.py:1383`、`agent/runtime/state.py:2826,2915`、`agent/runtime/loop.py:1274`。

成功 process 一律使旧验证失效，确实拦住了原先“成功写后旧证据仍有效”的缺陷。
但是批准的 local_process 仍会被准入为 mandatory `process_v1` criterion。tests 成功后再跑 lint，tests 的证据被作废；顺序交换也一样。
事后补跑 read-only sandbox 也不能满足已经绑定为 `process_v1` 的义务。

隔离复现使用现有 helper 形成 tests/lint 两个 mandatory criteria，经 `ClosedEvidenceRegistry.derive`：

```text
tests_then_lint: BLOCKED no exact process receipt proves the criterion
lint_then_tests: BLOCKED no exact process receipt proves the criterion
then_read_only_sandbox_retry: BLOCKED no exact process receipt proves the criterion
```

当前 read-only sandbox 正例（`tests/process/test_f1_input_mutation_invalidation.py:565`）手工构造 AdmittedCriterion 并调用 oracle。
它证明了“oracle 能验证这种数据”，没有证明“用户正常建 Goal、批准、运行、收尾可以产生这种数据”。
“最后一项有效”不能推出“全部 mandatory criteria 在有限步内共同有效”。原 A03 必须补生产路径证据。

最窄下一步：保留成功 mutation 失效规则，把已经选定的 read-only sandbox 验证接入现有 Goal/approval/receipt admission；不新建快照系统、不静默删除旧义务。

## 2. F3 验收设施仍有实际接线错误

这些主要影响 Dogfood 的可运行性与结论可信度，不应描述成普通聊天 CLI 完全不能启动。

### R2a：终态读取目录错误

`scripts/run_real_coding_scenario.py:145` 只读 `state_root/*.json`。
真实 `open_workspace_session` 写在 `state_root/workspaces/<scope>/<conversation-id>.json`。
调用真实 session 创建入口后，driver 稳定报 `expected exactly one ... found 0`。
现有 typed-status 测试把 checkpoint 人工写到顶层，绕开了生产布局。

### R2b：遗漏 required check，实际 run() 可误报 completed

`run_real_coding_scenario.py:447` 只在业务 grader 已返回 `product_ran_related_tests` 时补操作检查。
但 D01/D02/D03/D05 的业务 grader 不返回此键，manifest 却要求它；第 454 行的 `all(checks.values())` 因而漏掉必需项。

使用 D01 正确参考实现、stub 产品入口（零 provider）、令相关测试证明返回 False，调用实际 `run()`，得到：

```text
product_status: completed
checks: empty_rows / quoted_commas / existing_behavior
missing_required: product_ran_related_tests
validator: independent_checks_mismatch / completed_without_basis
```

正例必须覆盖实际 run→实际 validator，不能只测试 build_record_v2。

### R2c：孤立 passed EvidenceRecord 仍可冒充执行依据

`run_real_coding_scenario.py:163–207` 只查 criterion 前缀、Goal 绑定和 passed 字段，不查执行来源事实。
现有 helper 的 `state(facts=())` 实际仍返回 `(True, "")`。
`tests/acceptance/test_f3_driver_receipts.py:31` 还将旧 Goal 的失败 receipt 配手填 passed evidence 断言为 True。
该反例应当失败；正例要来自实际 Runtime 的准入/执行/验证链，并复用内核的证据验证能力。

### R2d：当前预算/记录合同缺少字段间约束

- preflight 只检查请求预算正数；用假环境值可复现 manifest 允许 1 次、args 配 30 次且 wall budget 为 0 仍接受。默认 manifest=false 目前阻止真实发送，但正授权路径还没闭合。
- validator 对 `model_identity=null`、`external_grader_runs=0`、`ledger_start=10/end=0`、`physical_requests=0` 的 completed 合成记录仍返回 RECORD_VALID。
- D04 的 `latest_correction` 仍仅由最终 alias 行为置 true；若字段表示运行中纠正，必须跟其他未观测过程项一样保留未验证，不能为了它新建旅程。

以上只需修现有 runner/validator 合同，不需要新 schema 平台或新评测体系。

## 3. F2 的主链可保留，但退出与测试驱动有小缺口

### R3a：UNKNOWN 清理会重复向已退出 worker 发 close，白等响应超时

`agent/browser/tools.py:822,840` 在 close UNKNOWN 后调用 environment.shutdown；
`agent/browser/playwright_adapter.py:635` 会对仍登记的 session 再次 close。
真实 adapter + fake Playwright，缩短 response timeout 到 0.15 秒的复现：

```text
close roundtrips / worker alive: [('close', True), ('close', False)]
elapsed_seconds: 0.15
error: BrowserCleanupUnknownError
ledger phase: active
```

默认 response timeout 为 60 秒。没有错误签 cleaned，但用户退出会无意义等待。
只需避免对已经退出的 worker 发第二个 cleanup 请求，同时保留 UNKNOWN/fail-closed。

### R3b：真实旅程驱动的失败清理/时间上限与声明不一致

- `scripts/f2_f3_local_browser_journeys.py:151–195` 的 F2 旅程没有 finally；用计数器替身模拟 open 后异常，cleanup 调用为 0。
- `main:387,402` 的预算只是函数返回后的 assert。设置 0.01 秒预算、注入耗时 0.08 秒的无浏览器 stub，0.092 秒后才抛断言，不能中断挂起。
- 全局 finally 只删临时目录，不能代替进程/浏览器收尾。D06 finally 中第一个 cleanup 抛错也可能跳过后一个。
- D06 用 li 数量增加作为观察层证明，不能单独证明提交的具体内容正确；冻结外部断言、产品 action/readback 和参考旅程证据需要准确分层，不必新增浏览器观察能力。

## 4. 可保留的成果与只需补证的部分

### F2 正常主链：接受，勿重写

同一 owner 的 close→CLEANED→ledger CLOSED→新 owner 补记链已接到 composition。
未复现 UNKNOWN、损坏记录、错误 browser identity 或 worker join 失败被错误签成 CLEANED。
正常幂等与 writer 释放可保留；SIGKILL/断电无证据仍 UNKNOWN 的限制合理。

### F4 顺序容量修复：接受；A20 仅补有效竞态测试

额外实测容量 2，连续创建并归档 **100** 个不同终态会话，inspection 成功，活动 snapshot 为 0，目录只剩 bootstrap lock。
因此不是简单把第 6 轮故障推迟。清扫 flock/inode 核对与 acquire 的 post-flock 重验均存在，未证实新的生产 split-lock 缺陷。

但 `tests/continuity/test_f4_lock_accumulation.py:143–153` 自己 open 旧 fd，随后调用 try_acquire 又重新 open 当前 pathname。
其返回 None 可由当前新锁被父进程占用解释，并没有测试 try_acquire 内部对旧 fd 的重验。
只需将实际 acquire 暂停在 open→flock 边界，再置换锁并继续，证明重验有效；不要重构锁方案。
旧版本进程没有新增重验，不能声称它们自动安全；保留“升级前退出相关旧进程”的边界，不替用户停止进程。
